# Roles

Status: draft, step 1 of the access plan. It defines who can do what. The tables each role needs an
RLS policy on, and the policies themselves, come in later steps.

## How a user gets a role

```
Supabase Auth (auth.users)  →  users (auth_user_id)  →  org_members (user_id, org_id, role)
   who you are                  your Sangam account       what you can do in each org
```

1. A user signs in with Supabase OAuth. Supabase creates a row in `auth.users`.
2. On the first request, the backend creates a `users` row linked to it by
   `users.auth_user_id = auth.users.id`. This is the default role: signed in, belonging to no org.
   The frontend sends the Supabase access token (a JWT) as `Authorization: Bearer <token>`; the
   backend (`app/core/security.py`) checks its signature against the project's public keys
   (`<SUPABASE_URL>/auth/v1/.well-known/jwks.json`), its expiry, `aud = authenticated` and its
   issuer, then takes the `sub` claim (the `auth.users.id`) and finds the `users` row whose
   `auth_user_id` matches. If none matches, it links a staff-pre-created row with the same email
   or creates a new one. A bad or expired token gets 401.
3. Access beyond that is granted by adding `org_members` rows (one per org) or by setting
   `users.is_staff = true`.

## Postgres roles: `anon` and `authenticated`

These are database roles that Supabase creates in every project by default. Supabase picks one from
the JWT's `role` claim: a request with no user session (only the public anon key) runs as `anon`,
and a signed-in user's access token carries `"role": "authenticated"`. (Supabase's API logs in as a
third role, `authenticator`, which then switches to whichever of the two the token names.) These two
say only whether someone is signed in; the roles below, from `users` and `org_members`, decide what
a signed-in user can see.

## The roles

| # | Role | Stored as | Who gets it | Reads | Writes | Features |
|---|---|---|---|---|---|---|
| 0 | Anonymous | Not signed in, Postgres role `anon` | Anyone visiting the site | Public content only | Nothing | Browse the public registry |
| 1 | Signed-in (default) | A `users` row with no `org_members` row, Postgres role `authenticated` | Everyone, automatically on first sign-in | Public content only, same as anonymous | Nothing | Browse the public registry, their own profile (`/api/me`). No Ask Sangam |
| 2 | Org member | `org_members.role = 'member'` | Added to an org by staff | Public content, plus that org's private data | That org's data: contacts, proposals, documents, RFP matches, score adjustments; their own chat threads | Ask Sangam, scoped to their org |
| 3 | Org admin | `org_members.role = 'admin'` | Added to an org by staff | Same as member | Same as member | Same as member, plus manage that org's users |
| 4 | Group Admin | `org_members.role = 'steward'`, one row per org | An ecosystem partner (e.g. Node), added by staff to each org it supports | Public content, plus the private data of every org it is added to | Nothing. Read-only | View its orgs' data and team threads shared with stewards |
| 5 | Staff | `users.is_staff = true` | The internal team only | Everything, every org | Everything, every org | Sangam Import (`/api/ingest/*`), pushing data, granting and removing access |

A user can hold different roles in different orgs, for example admin of org A and steward of org B.
Staff is global and does not need any `org_members` rows.

## What each role adds on top of the one before

```
Anonymous ─► Signed-in ─► Member ─► Admin          Staff (everything)
 public       + own         + read & write   + manage
              profile       own org's        org users
                            private data,
                            Ask Sangam
                                 │
                                 └─► Group Admin: read private data of its orgs, no writes
```

## Public tables: visible to `anon` and `authenticated`

A public table is readable by everyone, signed in or not. It needs two things: a grant, which lets
both roles read the table at all, and an RLS policy, which decides which rows they see. A fully
public table such as `programs` has a policy that lets every row through.

Only read access is granted, so neither role can write to a public table. Tables that are public but
hold some private rows (`orgs`, `funders`, `contacts`, `documents`, …) get the same read grant with a
narrower policy, for example `contacts` showing only public contacts and office bearers to `anon`.

## Functions that enforce it

### The idea in three lines

1. **RLS (row level security)** is a Postgres feature Supabase gives us: a rule on a table that runs on
   every read or write and decides, row by row, whether the caller is allowed.
2. **A rule needs to know about the caller**: who they are, are they staff, which orgs they are in.
   Supabase lets us add our own database functions (dashboard: **Database → Functions**) that answer
   those questions.
3. **So we write the answers once, as five functions, and every RLS rule calls them.**

### The five functions

| Function | The question it answers | Used for |
|---|---|---|
| `app.user_id()` | Which Sangam user is calling? | Own rows, such as chat threads |
| `app.is_staff()` | Is the caller staff? | Staff sees and writes everything |
| `app.my_org_ids()` | Which orgs can the caller **read**? For a member or admin, their org. For a Group Admin, every org they support, so it can be two or more org ids | Reading private org data |
| `app.my_writable_org_ids()` | Which orgs can the caller **write to**? (member or admin only) | Writing org data |
| `app.can_open_thread(thread, user)` | May this user open this chat? | The backend, before loading a conversation |

Each one starts by asking Supabase who is signed in (Supabase's built-in `auth.uid()`, which reads the
caller's token), then looks that person up in our `users` and `org_members` tables.

### Example: how `my_org_ids` and `my_writable_org_ids` restrict a table

Say there are two orgs, **Org A** and **Org B**, and four people:

| Person | Their `org_members` rows | `app.my_org_ids()` returns | `app.my_writable_org_ids()` returns |
|---|---|---|---|
| Member | Org A, role `member` | Org A | Org A |
| Admin | Org A, role `admin` | Org A | Org A |
| Group Admin | Org A and Org B, role `steward` | Org A, Org B | *(nothing)* |
| Signed-in, no org | none | *(nothing)* | *(nothing)* |

Now take the `proposals` table, which is org-private. It has two rules:

- **Read rule:** you see a proposal if its org is in `app.my_org_ids()`, or you are staff.
- **Write rule:** you can add or edit a proposal if its org is in `app.my_writable_org_ids()`.

What each person gets:

| Person | Sees proposals of | Can write proposals of |
|---|---|---|
| Member | Org A | Org A |
| Admin | Org A | Org A |
| Group Admin | Org A and Org B | Nothing: read-only |
| Signed-in, no org | Nothing | Nothing |
| Staff | Every org | Not through this rule (staff writes go through Sangam Import) |

The only thing that makes a Group Admin read-only is that they appear in `my_org_ids` but not in
`my_writable_org_ids`. Nobody filters by hand: the same two functions protect every org-private table.

### The same pattern across all tables

| Kind of data | Who gets it | Function the rule calls |
|---|---|---|
| Public (programs, grants, tags, …) | Everyone | none |
| Hidden registry rows (orgs, funders) | Staff only | `app.is_staff()` |
| Org-private data (proposals, RFP matches, private contacts and documents) | The org's members, admins, Group Admins, and staff | `app.my_org_ids()` |
| Writes to org data | The org's members and admins, never Group Admins | `app.my_writable_org_ids()` |
| Chat threads | The owner, the team if shared, and staff | `app.user_id()` |
| Import tables | Staff only | `app.is_staff()` |

### Why this way

- **One place for the rules.** The backend does not filter in each query, and a route that forgets a
  check still cannot return rows the caller should not see.
- **Changing access is just data.** Adding someone to an org is one `org_members` row; the functions
  pick it up on their next request, with no code change.
- **The functions are safe to call.** They run with the owner's rights (`SECURITY DEFINER`), so a rule
  can check `org_members` without the caller being able to read that table, and they only ever answer
  about the caller.

## To solve in another PR

### Open questions

1. **Gap: Ask Sangam ignores RLS.** This is the biggest security gap. A normal API request runs as the
   caller, so RLS filters what comes back. The chat agent's SQL tool (`db_query`) connects as the
   database owner, which skips RLS, so it can read everything.

   Fix: run the agent's queries as the caller, the same way API requests run (step 12). Until then,
   Ask Sangam must not be opened to non-staff users.

## End-to-end flow

```
 1. Sign in
    User ──► Supabase Auth (OAuth) ──► access token (JWT)
                                            │
 2. Request                                 ▼
    Frontend ──► Backend      Authorization: Bearer <token>
                    │
 3. Who is calling? ▼
    No token ────────────────► anonymous
    Bad or expired token ────► 401
    Valid token ─────────────► continue below

    Backend checks the token against Supabase's public keys
    (signature, expiry, audience `authenticated`, issuer = our project)
                    │
                    ▼
    Backend reads from the token:
      sub                         the Supabase user id (`auth.users.id`)
      email                       the user's email     (missing ──► 401)
      user_metadata.full_name     display name, if the OAuth provider sent one
                    │
                    ▼
    Backend finds the Sangam account in our `users` table, in this order:
      a. a row with this auth_user_id  ──► use it (update the email if it changed)
      b. a row staff created with this email and no auth_user_id yet
                                       ──► link it: set auth_user_id = sub
      c. neither                       ──► create a new row (email, auth_user_id, name)
      Email already linked to a different Supabase account ──► 409
                    │
 4. Route check     ▼   (the backend checks the kind of request before any query)
    Reading, e.g. the registry ──► anyone, signed in or not
    Saving or editing data     ──► must be signed in         else 401 "Sign in required"
    Sangam Import              ──► must be staff             else 403 "Staff only"
    Ask Sangam chat            ──► must be signed in, and the chat must be yours
                                   someone else's chat ──► 404, as if it does not exist
                    │
 5. Query as the caller
                    ▼
    Database role: `anon` (signed out) or `authenticated` (signed in)
    + the caller's Supabase id, which `auth.uid()` returns
                    │
 6. RLS on the table▼
    First, the grant: may this role touch the table at all?
      no  ──► 403   (e.g. `anon` reading `proposals`, anyone reading checkpoint tables)
      yes ──► the table's RLS rules run, row by row
                    │
                    ▼
    Read rule  ── decides which rows come back; the rest are silently left out
    Write rule ── checks the new or changed row; refused ──► 403

    Which rule a table gets: see "Which rule each table gets" below

    The rule calls the functions:
      app.is_staff()             staff?             ──► every row
      app.my_org_ids()           orgs I can read    ──► rows of those orgs
      app.my_writable_org_ids()  orgs I can write   ──► writes to those orgs only
      app.user_id()              me                 ──► my own rows (threads)
                    │
                    │   the functions look up `users` and `org_members`
                    ▼
 7. Response
    Only the rows this caller may see, or 403 if a write is refused
```

### Which rule each table gets

| Kind | Who sees the rows | Tables |
|---|---|---|
| Public | Everyone | programs, grants, tags, locations, … |
| Public unless hidden | Everyone, except rows marked hidden, which only staff see | orgs, funders |
| Public by flag | Rows marked public go to everyone; the rest only to that org's people and staff | contacts, documents, org identifiers, news |
| Org-private | Only that org's people and staff. Never anyone signed out | proposals, RFP matches |
| Own rows | Only you, plus your team for a chat they share with you, and staff | users, chat threads |
| Staff only | Staff | Sangam Import tables |
| Closed | Nobody through the app | chat checkpoints, migration history |
