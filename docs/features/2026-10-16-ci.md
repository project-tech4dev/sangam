# CI for backend and frontend, coverage, and PR bots

## Context
The repo has no CI apart from the hand-run `deploy.yml` and the `dependency-review.yml` added in #233. Nothing checks a PR before it merges: lint, types, the 1188 backend unit tests, the 18 integration test files, or the frontend build. Many PRs here are written by AI agents, so the checks have to be automatic, and an AI reviewer should read every PR. The goals:
- every PR runs backend and frontend checks plus the integration tests against a real Postgres;
- coverage is shown on the PR, and the PR fails if total coverage drops;
- Dependabot and an AI reviewer run on every PR.

Decisions already made:
- **Coverage:** report it, and fail only on a drop (a ratchet).
- **Frontend:** lint, type check and build only; a test runner comes in a later PR.
- **Integration tests:** run on every PR.
- **Bots:** an AI PR reviewer and Dependabot.

Following the repo's conventions, this is two stacked PRs on top of #233 (`fix/dependabot-alerts`). The plan is committed first as `docs/features/2026-10-16-ci.md`.

## M1: `ci.yml` (PR 1)
`.github/workflows/ci.yml` runs `on: pull_request` and on `push` to `master`.
- **Top level:** `permissions: contents: read`, a `concurrency` group per ref with `cancel-in-progress: true`, and `timeout-minutes` on every job.

| Job | Steps |
|---|---|
| `backend-lint` | `astral-sh/setup-uv`, `uv sync --frozen`, `ruff check .` (no `ruff format --check`: the repo doesn't use ruff's formatter yet) |
| `backend-unit` | `uv run pytest -m "not integration" --cov=app --cov-report=xml:coverage-unit.xml`; uploads the coverage data file |
| `backend-integration` | A service container `pgvector/pgvector:pg17` on 5433, the same image as `docker-compose.yml`. Steps: apply `db/init/0*.sql` with `psql`, run `python -m app.db.migrate` with `MIGRATIONS_DIR=db/migrations`, run `python -m seed.seed` and `seed.taxonomy_seed` from the repo root (the Makefile `seed` target, without Docker), then `pytest -m integration --cov=app`. `TEST_DATABASE_URL` points at the service, matching `tests/conftest.py:51`. |
| `coverage` | needs both test jobs. It runs `coverage combine`, then `coverage report --fail-under` (the ratchet), then `diff-cover coverage.xml --compare-branch=origin/master`, which reports only. It writes both to `$GITHUB_STEP_SUMMARY` and keeps one sticky PR comment updated (`marocchino/sticky-pull-request-comment`, `pull-requests: write` on this job only). |
| `frontend` | `actions/setup-node` with the npm cache, `npm ci`, `npm run lint`, `npx tsc --noEmit`, `npm run build` (CLAUDE.md: type errors only surface in the build). Dummy `NEXT_PUBLIC_SUPABASE_*` values so the build doesn't need secrets. |

Backend changes this needs:
- `backend/pyproject.toml`:
  - add `pytest-cov`, `diff-cover` and a pinned `ruff==0.16.8` to the `dev` group;
  - add `[tool.coverage.run] source=["app"] branch=true` and `[tool.coverage.report] fail_under=<measured baseline, rounded down>`;
  - add `[tool.ruff.lint] ignore=["B008"]` (FastAPI's `Depends()` idiom accounts for 50 of today's 85 errors) and `"RUF012"` (26 class-level constants).
- Fix the remaining 9 errors: 7 `DTZ011` (`date.today()`), 1 `UP046`, 1 `I001`. That makes `ruff check` green on master.
- Raising the ratchet is a one-line PR that edits `fail_under` whenever coverage grows.

Risks to check while building:
- Whether the seed scripts run outside Docker. They run from the repo root (`seed/` sits next to `backend/`), so `PYTHONPATH=backend` plus `DATABASE_URL` may be enough.
- Whether `_verify_sql_catalog` matters. Integration tests don't boot the app, so it shouldn't.

**Exit gate:** PR 1 shows every job green, a coverage comment on the PR, and a step summary. A scratch commit with `fail_under=99` turns the `coverage` job red, which proves the gate works; the commit is then reverted.

## M2: Bots and repo hygiene (PR 2, stacked on PR 1)

**`.github/dependabot.yml`:**
- three ecosystems: `npm` (`/frontend`), `uv` (`/backend`) and `github-actions` (`/`), each checked weekly;
- `groups` so minor and patch updates arrive as one PR per ecosystem;
- an `ignore` for `@copilotkit/*` at ≥1.76 until the AG-UI 1.0 migration happens (#233 explains why).

Security PRs keep coming in separately once you turn on "Dependabot security updates" in Settings.

**`.github/workflows/claude-review.yml`:** `anthropics/claude-code-action@v1` reviews each PR when it's opened, updated or marked ready for review.
- It runs on `pull_request`, never `pull_request_target`. Fork PRs therefore get no secrets and the job skips them, which is the safe default for a public repo.
- It skips `dependabot[bot]` and draft PRs.
- Model: Sonnet 5.5, to keep cost per review low. One secret: `ANTHROPIC_API_KEY`.
- The prompt asks it to review against `CLAUDE.md` and the repo rules: tools never raise, citations, `guarded_client`, migrations not edits to `02_schema.sql`, catalog = security decision, no inline styles, short comments. It posts inline comments and never pushes.
- Also `@claude` on demand: `issue_comment` and `pull_request_review_comment` triggers, limited to repo collaborators (`author_association` check).

**Hygiene:**
- `.github/pull_request_template.md`: what changed, how it was tested, and checkboxes for `make wiki-update`, ARCHITECTURE.md and CHANGELOG (from CLAUDE.md).
- `.github/CODEOWNERS`: `db/migrations/`, `backend/app/agent/tools/sql/catalog.py`, `.github/` and `backend/app/core/security.py` need an owner's review.
- Actions pinned to a major version now. Dependabot `github-actions` keeps them current.

**For you to do in GitHub settings** (no file can do these):
- branch protection on `master`, requiring `backend-lint`, `backend-unit`, `backend-integration`, `coverage`, `frontend` and `Dependency review`, plus one approving review;
- turn on Dependabot security updates and secret scanning with push protection;
- add the `ANTHROPIC_API_KEY` secret.

**Exit gate:** a test PR gets a Claude review comment; `@claude` in a comment gets a reply; Dependabot's first run opens grouped PRs, visible in Insights → Dependency graph → Dependabot.
